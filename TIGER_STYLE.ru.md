# TigerStyle для вашего кода

> Перевод ревизии r5 руководства [Adapting TigerStyle to Your Codebase](TIGER_STYLE.md). Если перевод расходится с оригиналом, действует английский текст.

TigerStyle — стиль программирования базы данных TigerBeetle. На первом месте в нём безопасность, на втором — производительность, на третьем — удобство разработчика, и каждое правило служит одной из этих целей. Это руководство излагает стиль заново для других кодовых баз и указывает, насколько далеко распространяется каждое правило.

Многие механизмы TigerStyle создавались для системного программирования, где программа явно управляет памятью и другими ресурсами. В других условиях они часто применимы как цели, но не как механизмы. Поэтому правила разделены на три уровня: базовые требования, решения профиля проекта и локальные соглашения. Блоки, которые подходят лишь части проектов, начинаются со строки о том, когда они применяются.

Это независимая переработка [TigerStyle](https://github.com/tigerbeetle/tigerbeetle/blob/main/docs/TIGER_STYLE.md). Основные правила принадлежат авторам оригинала. Формулировки, три уровня, строки применимости, примеры, а также разделы о безопасности, внедрении и различиях между языками добавлены здесь. Несколько правил намеренно мягче оригинала; там, где число или запрет ослаблены, в тексте приведена собственная настройка TigerStyle. Каждое правило — это указание в повелительном наклонении и его обоснование.

## Коротко

Руководство в десяти строках:

- Сначала безопасность, затем производительность, затем удобство разработчика.
- Правило применяется только там, где есть его предмет, а профиль перечисляет действующие специальные блоки.
- У каждого ресурса есть лимит, и для каждого лимита задана реакция.
- Данные извне враждебны, пока их не разобрали на границе.
- Каждая ошибка обрабатывается, а пути обработки ошибок покрыты тестами.
- Полномочия задаются явно: запрещать по умолчанию и проверять в точке использования.
- Внутренние инварианты проверяются утверждениями (`assert`), а при сработавшем утверждении действует записанная политика.
- Память, рекурсия, конкурентность и числовые лимиты определяются один раз — в профиле проекта.
- Именование и оформление следуют сначала языку, а затем этому руководству.
- Изменение исправляет то, что затрагивает, и фиксирует то, чего не исправляет.

## Область действия и приоритет

Чего правило требует от проекта, решают два вопроса. Применимо ли оно здесь? Если да, насколько оно обязательно?

### Применимость

Правило применяется там, где есть его предмет: входные данные, ресурс, механизм или требование, о котором оно говорит.

- **Применяйте общее ядро везде, где появляется его предмет.** Большинство правил касается того, что делает почти любая программа: принимает входные данные, обрабатывает сбои, ограничивает объём работы и задаёт контракты. Каждое из них действует там, где это происходит: правило о внешних данных действует везде, где такие данные попадают в систему.
- **Включайте специальный блок по его условию.** Некоторые правила предполагают определённый механизм или требование: явное управление памятью, собственный протокол, повышенные привилегии или жёсткий бюджет задержки. Они обязательны только для проекта, в котором это есть. Каждый такой блок начинается со строки о том, когда он применяется, а отдельное условное правило само называет своё условие.
- **Не записывайте неприменимость как исключение.** Правило, предмета которого нет, находится вне области действия, и для него не нужны ни обоснование, ни ответственный. Иначе обычному проекту пришлось бы оправдываться за то, что он не инфраструктурная система.

### Уровни

Применимые правила обязательны не в равной мере. Каждый раздел помечен одним из трёх уровней, и более высокий уровень главнее.

| Уровень | Что охватывает | Кто решает | Разделы |
| --- | --- | --- | --- |
| Базовое требование | Проверка недоверенных входных данных, обработка ошибок, ограничение ресурсов, контроль полномочий | Никто: там, где оно применимо, оно действует в любой кодовой базе и на любом языке | Лимиты и ошибки; Безопасность |
| Профиль проекта | Стратегия работы с памятью, рекурсия, модель конкурентности, политика утверждений, проектирование под производительность, зависимости | Проект — один раз и письменно | Поток управления; Утверждения; Состояние, память и числа; Производительность; Зависимости и инструменты |
| Локальное соглашение | Именование, длина строки, размер функции, порядок аргументов, форма комментариев и коммитов | Сначала экосистема языка, затем проект | Функции; Именование; Комментарии, коммиты и оформление |

- **Считайте уровень раздела уровнем по умолчанию.** Некоторые правила относятся не к тому уровню, что их раздел. Каждое из них несёт собственную метку, и эта метка главнее.
- **Отдавайте приоритет более высокому уровню.** Базовое требование главнее решения профиля, а решение профиля главнее соглашения. Если функция укладывается в лимит строк только ценой удаления проверки ошибки, оставьте проверку.
- **Отдавайте приоритет языку перед соглашением.** Если в экосистеме есть стандартный форматтер, схема именования или порядок аргументов, следуйте им. Соглашение существует ради единообразия, а экосистема — больший объём кода, с которым нужно согласовываться.
- **Пусть язык влияет на профиль, но не на базовые требования.** Среда со сборкой мусора меняет то, как вы ограничиваете память. Она не меняет того, ограничиваете ли вы её вообще.
- **Сохраняйте цель, когда меняете механизм.** Если механизм правила не подходит, замените его другим, который служит той же цели, и запишите этот выбор в профиль.
- **Считайте настройки TigerStyle лишь одним примером профиля.** Его числа и запреты выбраны для базы данных. Другое значение в вашем профиле само по себе не означает более низкую планку. Оценивайте каждую настройку по тому, что требуется проекту.
- **Обеспечивайте соблюдение заданных лимитов.** Когда профиль задал лимит, его соблюдение проверяют инструменты, и его не пересматривают от случая к случаю. Единственное исключение — плотность утверждений (*Считайте плотность утверждений сигналом, а не нормой*).
- **Записывайте каждое исключение из правил.** Укажите в профиле его область, причину и ответственного. Отразите его в автоматической проверке как подавление ровно этой области и сошлитесь из кода на запись в профиле. От базового требования никогда не отказываются — его лишь выполняют другим механизмом.

## Принципы

Любой вопрос стиля решают три цели в таком порядке: безопасность, производительность, удобство разработчика.

- **Ранжируйте цели.** Важны все три. Когда они расходятся, безопасность важнее производительности, а производительность важнее удобства разработчика.
- **Относитесь к стилю как к проектированию.** Оценивайте каждый выбор по тому, приближает он к трём целям или отдаляет от них. Читаемость — входной билет, а не цель.
- **Добивайтесь простоты.** Простое решение редко бывает первым черновиком. Обычно это та единственная идея, которая служит всем трём целям сразу. Продолжайте искать варианты, пока не найдёте её, и будьте готовы выбросить черновик.
- **Думайте, прежде чем строить.** Проектирование — самый дешёвый этап проекта. Реализация, тестирование и годы эксплуатации обходятся намного дороже, поэтому всё обдумайте до того, как появится код.
- **Не добавляйте технического долга.** Изменение выходит без собственных известных дефектов. Исправьте то, что вносите, и то, что затрагиваете, до слияния, потому что дешевле, чем сейчас, это уже не будет.
- **Записывайте то, что выходит за рамки изменения.** Проблему, найденную за пределами текущего изменения, заводят задачей в трекере, а не переписывают попутно. Каждое изменение должно быть небольшим и касаться одной задачи. Это относится и к ИИ-агентам: никакого постороннего рефакторинга в рамках небольшой задачи.
- **Не пропускайте блокирующих дефектов.** Известный порог, за которым задержка резко растёт, неограниченный рост или экспоненциальный алгоритм не попадают в релиз в том коде, который вы меняете, каким бы маловероятным ни было условие их срабатывания.
- **Выпускайте меньше, но надёжно.** Отсутствие функции допустимо; функция, которая не отвечает целям, — нет. Пересмотреть решение, когда вы узнали больше, — нормально. Выпускать то, что, как вы уже знаете, сломано, — нет.
- **Предпочитайте малое.** Чем меньше кода, абстракций и движущихся частей, тем меньше мест для ошибки.
- **Объясняйте причины.** Указывайте причину для каждого правила, решения и неожиданной строки. Причина позволяет читателю оценить выбор и понять, когда он перестал быть применим.

## Лимиты и ошибки

**Уровень:** базовое требование

На любом языке у каждого ресурса есть лимит, а у каждого сбоя — обработчик.

### Лимиты

- **Ограничивайте всё.** У каждого цикла, очереди, буфера, пакета, повторной попытки и ожидания есть фиксированная верхняя граница. Реальные системы конечны, поэтому укажите, где проходит край.
- **Определите, что происходит на лимите.** Выберите реакцию для каждого лимита: отклонить, включить обратное давление, сбросить нагрузку или остановиться. Затем при превышении лимита реагируйте немедленно, потому что лимит без заданной реакции — всего лишь надежда.
- **Помечайте циклы, которые никогда не завершаются.** Цикл событий — единственное исключение. Сразу после такого цикла поставьте утверждение, что код за ним недостижим.

### Ошибки и тесты

- **Обрабатывайте каждую ошибку.** Никаких проигнорированных кодов возврата и пустых блоков catch. [Исследование отказов в промышленной эксплуатации](https://www.usenix.org/system/files/conference/osdi14/osdi14-paper-yuan.pdf) распределённых систем показало, что 92% катастрофических отказов вызваны нефатальными ошибками, которые были обработаны неправильно.
- **Тестируйте пути обработки ошибок.** В большинстве систем код обработки ошибок проверяется меньше всего. По данным того же исследования, простые тесты кода обработки ошибок выявили бы дефект, стоящий за 58% катастрофических отказов.
- **Тестируйте обе стороны.** Подавайте в тесты корректные данные, некорректные данные и данные на переходе от корректных к некорректным.
- **Описывайте каждый тест.** Начинайте тест с короткого пояснения его цели и метода, чтобы читатель мог разобраться в нём или пропустить его. **Уровень:** локальное соглашение

## Безопасность

**Уровень:** базовое требование

Защита от атак — это та же безопасность, но в присутствии противника. Безопасность спрашивает, что произойдёт, если входные данные окажутся неверными случайно; защита от атак — что произойдёт, если их кто-то подберёт намеренно. Остальные правила уже устраняют целые классы атак, а этот раздел добавляет то, что меняет появление противника.

### Модель угроз

- **Пишите модель угроз до кода.** Достаточно одной страницы. Перечислите, что вы защищаете, кто и как может атаковать, где меняется уровень доверия и от чего вы сознательно не защищаетесь. Для безопасности она делает то же, что набросок на бумаге — для производительности.
- **Исходите из того, что атакующий прочитал исходный код.** Безопасность держится на ключах и проверках, а не на том, что устройство системы остаётся в тайне.
- **Пересматривайте модель, когда меняется поверхность атаки.** Новый источник входных данных, эндпоинт, привилегия или зависимость меняют модель угроз, и ревью такого изменения проводится именно с этой точки зрения.

### Границы доверия

- **Считайте враждебным всё, что пересекает границу.** Это относится к сети, файлам, переменным окружения, другим процессам и арендаторам, а также к вашему собственному хранилищу, если в него может писать кто-то ещё.
- **Разбирайте на границе.** В одном месте преобразуйте недоверенные байты в типизированные значения, которые не могут представить недопустимое состояние ([Parse, don't validate](https://lexi-lambda.github.io/blog/2019/11/05/parse-don-t-validate/)). Код внутри границы принимает только эти типы и никогда не видит сырых входных данных.
- **Разрешайте допустимое и отвергайте остальное.** Определите множество допустимых значений и отказывайте во всём, что в него не входит. Проверьте сообщение целиком, прежде чем любая его часть вступит в силу.
- **Принимайте для каждого значения одну кодировку.** Отвергайте неканонические формы. Два компонента, которые по-разному читают одни и те же байты, оставляют атакующему лазейку.
- **На границе возвращайте ошибки, за ней ставьте утверждения.** Некорректные данные извне — это эксплуатационная ошибка: её ожидают и обрабатывают. Утверждение (`assert`), которое могут сорвать внешние данные, — это удалённый выключатель вашего сервиса.
- **Никогда не смешивайте данные с командами.** Не собирайте SQL, команды оболочки, HTML, пути к файлам, форматные строки или строки журнала склейкой строк с недоверенными данными. Используйте параметризованные интерфейсы, кодируйте вывод с учётом места, куда он попадает, и никогда не десериализуйте недоверенные данные в объекты произвольных типов.

### Лимиты как защита

- **Ограничивайте до выделения памяти.** Сверяйте каждую заявленную длину, количество, глубину вложенности и размер после распаковки с максимумом, прежде чем выделять под них память. Поле длины — это заявление, а не факт.
- **Ограничивайте время.** У каждого ожидания есть тайм-аут, у каждой серии повторных попыток — предел, а у каждого запроса — крайний срок, который покрывает все его шаги.
- **Дайте каждому клиенту бюджет.** Установите квоту на каждый общий ресурс, чтобы один клиент не мог лишить ресурсов остальных. При перегрузке отказывайте рано и дёшево.
- **Тратьте меньше, чем атакующий.** Выполняйте дешёвые проверки — размера, формата, квоты — раньше дорогих.
- **Не усиливайте трафик на непроверенный адрес.** Некоторые транспорты, например UDP, позволяют отправителю подделать свой адрес. В них ответ не должен превышать полученные данные больше чем в несколько раз, пока удалённая сторона не докажет, что принимает данные по этому адресу. В остальных случаях большой ответ на маленький запрос допустим — с аутентификацией пользователя или без неё.
- **Рассчитывайте на худший случай.** Когда входные данные выбирает атакующий, скорость в среднем случае не имеет значения. Для хеш-таблиц с ключами извне используйте хеширование с секретным ключом, для сопоставления с шаблоном — алгоритмы с линейным временем, а парсеры пишите без квадратичных путей.

### Память и арифметика

- **Предпочитайте языки, безопасные по памяти.** Где это невозможно, ограничьте небезопасный код небольшими помеченными модулями. Проводите их фаззинг под санитайзерами и поставляйте сборки со всеми включёнными защитными механизмами инструментария и проверками выхода за границы.
- **Выбирайте поведение при переполнении явным именем операции.** По умолчанию арифметика проверяет переполнение, если только код явно не указывает арифметику с переносом или с насыщением. Проверяйте вычисления размеров, например количество, умноженное на размер элемента, прежде чем результат попадёт в аллокатор или в операцию копирования.
- **Никогда не отдавайте устаревшую память.** Инициализируйте то, что выделяете, и обнуляйте неиспользуемую часть буфера, прежде чем он пересечёт границу.

### Секреты

**Применяется, когда:** программа работает с ключами, паролями, токенами или другими секретами.

- **Не допускайте секреты в исходный код, журналы, сообщения об ошибках, URL и метрики.** Оборачивайте каждый секрет в тип, который при выводе печатает заглушку, чтобы раскрыть секрет можно было только намеренным вызовом. Это предотвращает случайный вывод. Из памяти байты при этом никуда не исчезают.
- **Задайте политику для дампов памяти.** Дамп памяти или снимок кучи содержит все секреты, которые загрузил процесс. Решите, отключены ли дампы, ограничен ли доступ к ним или секреты из них вычищаются, и обращайтесь с любым дампом как с секретным материалом.
- **Держите мало копий и недолго.** Загружайте секрет как можно позже, передавайте его по ссылке и отбрасывайте, когда операция завершится. Каждая копия и каждая секунда увеличивают риск раскрытия.
- **Знайте пределы затирания.** Где вы управляете памятью, стирайте секрет вызовом обнуления, который компилятор не удалит. В среде со сборкой мусора неизменяемые строки и перемещённые объекты оставляют копии, до которых не добраться, поэтому используйте изменяемые байтовые буферы и короткое время жизни.
- **Сравнивайте секреты за постоянное время.** Сравнение, которое останавливается на первом отличии, сообщает атакующему, какая часть догадки верна.
- **Делайте каждый секрет узким, короткоживущим и заменяемым.** Один ключ — одно назначение. Встройте ротацию секретов с самого начала и регулярно отрабатывайте её, потому что утечку секрета, который нельзя ротировать, уже ничем не исправить.
- **Ротируйте то, что утекло.** Секрет, попавший в репозиторий, журнал или чат, скомпрометирован. Удаление из истории этого не отменяет.

### Криптография

**Применяется, когда:** код выбирает, настраивает или вызывает криптографию. Если используется готовый защищённый транспорт, правила проектирования протоколов обязательны для этого транспорта; приложение его только настраивает.

- **Не изобретайте криптографию.** Используйте стандартные протоколы и проверенные, поддерживаемые реализации через их интерфейс самого высокого уровня: «запечатай это сообщение», а не «выполни этот блочный шифр».
- **Ограничьте набор принимаемых алгоритмов.** Настройте короткий список современных алгоритмов и отвергайте остальные. Никогда не откатывайтесь к более слабому варианту, если согласование не удалось.
- **Защищайте результат согласования.** Рукопожатие должно аутентифицировать согласованные параметры, чтобы атакующий посередине канала не мог навязать более слабый вариант.
- **В собственном протоколе фиксируйте один набор шифров на версию.** Один набор шифров на версию убирает согласование алгоритмов и всю связанную с ним сложность. Версию по-прежнему можно понизить, поэтому аутентифицируйте выбор версии и отвергайте версии, которые больше не разрешены.
- **Аутентифицируйте, прежде чем интерпретировать.** Используйте аутентифицированное шифрование и проверяйте подпись или тег до того, как разбирать данные, которые они покрывают, или действовать на их основе.
- **Берите случайность только из криптостойкого генератора операционной системы.** Передавайте этот источник как зависимость, чтобы тесты оставались детерминированными, а продакшен не мог откатиться к слабому источнику.
- **Сделайте повторное использование невозможным по построению.** Nonce никогда не повторяется для одного ключа. Ключ, хеш или подпись, созданные для одной цели, отвергаются для любой другой, поэтому включайте назначение, версию и контекст в подписываемые данные.

### Полномочия

- **Запрещайте по умолчанию и при сбое отказывайте.** Доступ требует явного разрешения. Если проверка завершилась ошибкой, истекла по тайм-ауту или не смогла принять решение, ответ — «нет».
- **Проверяйте права в точке использования.** Аутентифицируйте один раз на границе, а затем при каждой операции проверяйте, что этот субъект может выполнить это действие над этим объектом. Никогда не полагайтесь на проверку, которую выполнил клиент.
- **Проверяйте и используйте один и тот же объект атомарно.** Откройте файл и проверьте его дескриптор, вместо того чтобы проверить путь и открыть файл позже. Любой зазор между проверкой и использованием принадлежит атакующему.
- **Получите ресурсы при запуске, затем сбросьте привилегии.** Если программа стартует с правами, которые позже ей не понадобятся, откройте нужные ей сокеты, файлы и ключи. Затем откажитесь от права получать новые. Это правило *Выделяйте память при запуске и больше не выделяйте* в применении к полномочиям. **Уровень:** профиль проекта
- **Передавайте полномочия явно.** Функция получает дескриптор, который ей разрешено использовать, как аргумент и не имеет неявного доступа к файловой системе, сети или учётным данным. Тогда её сигнатура показывает, к чему она может прикоснуться.
- **Держите парсеры подальше от ключей.** Компонент, который обрабатывает недоверенные входные данные, не хранит секретов и имеет минимум привилегий. Компонент, который хранит ключи, разбирает как можно меньше.
- **Сокращайте поверхность атаки.** Каждый эндпоинт, флаг, возможность и отладочный хук — это поверхность атаки. Удаляйте неиспользуемое, делайте безопасной конфигурацию по умолчанию, а небезопасным параметрам давайте имена, которые об этом прямо говорят.

### Ошибки, журналы и данные

- **Сообщайте посторонним мало, а операторам — достаточно.** Ошибки, которые возвращаются через границу, единообразны и не раскрывают внутреннего устройства. По содержимому, размеру и времени ответа не должно быть видно, какая проверка не прошла.
- **Журналируйте события безопасности.** Записывайте, кто, что и когда сделал и с каким результатом: входы в систему, отказы в доступе, изменения привилегий, использование ключей. Ведите журналы только на дозапись, с ограниченным объёмом, без секретов и персональных данных.
- **Храните меньше данных и меньше времени.** То, что вы никогда не собирали, не может утечь. У времени жизни данных, как и у всего остального, есть верхняя граница.

### Цепочка поставок

- **Относитесь к зависимости как к участнику с правом коммита.** Её авторы и авторы всего, что она подтягивает, выполняют код с вашими привилегиями. Это довод безопасности в пользу правила *Стремитесь к нулю зависимостей*.
- **Фиксируйте каждую зависимость по хешу.** Коммитьте lockfile, по возможности кладите исходники зависимостей в репозиторий и собирайте проект, не загружая ничего незафиксированного.
- **Обновляйте осознанно.** Обновляйте по одной зависимости за раз, читайте, что изменилось, и подпишитесь на уведомления об уязвимостях для всех зависимостей.
- **Защитите сборку.** Сборки воспроизводимы из зафиксированных инструментов. Недоверенные pull request не получают секретов, а ключи подписи релизов не хранятся на машинах, где выполняется недоверенный код.
- **Требуйте второго ревьюера.** Каждое изменение до слияния читает второй человек, чтобы ошибка одного человека или одна украденная учётная запись не могли изменить код в одиночку. **Уровень:** профиль проекта

### Проверка и реагирование

- **Атакуйте свои границы в тестах.** Подавайте на каждую некорректные, слишком большие и обрезанные входные данные. Проверяйте утверждениями, что такие данные отвергаются и что никакое несанкционированное изменение не доходит до состояния приложения.
- **Определите поведение при дубликатах, переупорядочивании и повторах.** Протокол решает, что происходит в каждом случае: отвергнуть, дедуплицировать, переупорядочить или обработать идемпотентно. Тестируйте это поведение. Журналы аудита и счётчики ограничения частоты при этом могут меняться, и тесты должны это допускать.
- **Непрерывно проводите фаззинг каждого парсера.** Сохраняйте каждый вход, который вызвал падение, как постоянный регрессионный тест.
- **Симулируйте злонамеренную удалённую сторону, а не только неисправную.** Случайные сбои находят случайные ошибки. Противник выбирает худший момент намеренно.
- **Ставьте утверждения только на то, что модель выполнения сохраняет стабильным.** Права доступа могут измениться между двумя проверками, поэтому повторный отказ — обычный отказ, а не нарушенный инвариант. Перепроверяйте доступ по правилу *Проверяйте права в точке использования*, а утверждения оставьте для внутренних инвариантов.
- **Не копите долг по безопасности.** Известная уязвимость — это блокирующий дефект, и её исправляют сразу при обнаружении. Затем устраните весь класс: добавьте тип, утверждение, правило линтера или цель для фаззинга, которые остановят родственные уязвимости.
- **Будьте готовы до первого сообщения об уязвимости.** Опубликуйте, как конфиденциально сообщить об уязвимости, и отрепетируйте выпуск исправления.

## Поток управления

**Уровень:** профиль проекта

Поток управления должен быть настолько простым, чтобы читатель видел каждый путь и каждую границу.

- **Делайте поток управления простым и явным.** Используйте обычные ветвления и циклы, которые читатель может проследить глазами. Хитрая диспетчеризация и скрытые переходы создают пути, которые никто не проверяет.
- **Запретите рекурсию или ограничьте её.** TigerStyle запрещает рекурсию: цикл с заявленной границей показывает, что выполнение завершится, а стек не растёт. Там, где рекурсия — идиома языка, рекурсивно обходите только данные с известной границей или передавайте явный лимит глубины. Проверяйте лимит перед каждым следующим вызовом и отвергайте входные данные, которые бы его превысили.
- **Используйте мало абстракций, и только отличные.** У каждой абстракции есть цена, и каждая может протекать. Оставляйте абстракцию, только если она моделирует предметную область лучше, чем простой код.
- **Задавайте темп сами.** Не реагируйте напрямую на каждое внешнее событие. Ставьте события в очередь и обрабатывайте их ограниченными пакетами по собственному расписанию. Тогда объём работы за один такт определяет сама программа, а не вызывающий её код.

## Утверждения

**Уровень:** профиль проекта

Утверждение (`assert`) выражает внутренний инвариант, который, по убеждению программиста, выполняется всегда. Что происходит, когда утверждение срабатывает, — это политика, которую нужно выбрать и записать.

- **Понимайте, с какой ошибкой имеете дело.** Переполненный диск или оборванное соединение — эксплуатационная ошибка: она обязательно случится, поэтому напишите код, который её обрабатывает. Нарушенный внутренний инвариант — ошибка программиста: состоянию больше нельзя доверять.
- **Решите, что делает сработавшее утверждение.** По умолчанию оно останавливает процесс или хотя бы ту единицу работы, состояние которой под подозрением. Запишите эту политику, потому что утверждение может бросить перехватываемое исключение, завершить лишь одну задачу или вовсе быть удалено при компиляции.
- **Никогда не продолжайте работу на подозрительном состоянии.** Какой бы ни была политика, код не должен перехватывать срабатывание утверждения и продолжать работу с данными, на которых оно сработало. Изолируйте всё, чего могла коснуться сбойная единица работы. Возобновляйте работу только из состояния, которое заново построила проверенная процедура восстановления.
- **Сделайте остановку безопасной.** Остановка ограничивает ущерб, но не отменяет уже выполненные записи. Сохраняйте согласованность хранимых данных после внезапной остановки — атомарными записями или путём восстановления — и тестируйте восстановление.
- **Не отключайте утверждения в продакшене.** Сбой, пойманный на инварианте, обходится дешевле, чем испорченные данные, найденные позже. Проверьте конфигурацию сборки: многие инструментарии вырезают утверждения из релизных сборок.
- **Проверяйте, прежде чем вычислять.** Проверяйте утверждениями аргументы на входе, результаты на выходе и инварианты между ними. Непроверенные данные никогда не должны доходить до логики функции.
- **Считайте плотность утверждений сигналом, а не нормой.** В TigerStyle это в среднем два утверждения на функцию, и именно плотность делает фаззинг окупаемым. Функция, которая сильно не дотягивает до значения из профиля, заслуживает внимательного взгляда на ревью, но сборку не ломает. Утверждение, которое не может сработать или повторяет строку над собой, добавляет шум, а не безопасность.
- **Ставьте утверждения парами.** Проверяйте одно и то же свойство в двух местах, куда оно приходит разными путями. Проверяйте сообщение там, где его кодируют, и ещё раз там, где его декодируют. Тогда ошибке придётся проскочить мимо обеих проверок ([It Takes Two to Contract](https://tigerbeetle.com/blog/2023-12-27-it-takes-two-to-contract)).
- **Проверяйте обе стороны.** Проверяйте то, что должно произойти, и то, что не должно произойти никогда. Ошибки скапливаются на границе, где корректные данные становятся некорректными.
- **Ставьте в каждое утверждение одно условие.** Пишите `assert(x > 0); assert(x < limit);`, а не одно утверждение, которое объединяет оба условия через `and`. Тогда при срабатывании видно, какое именно условие нарушено.
- **Выражайте импликацию утверждением под условием.** `if (is_final) assert(pending_count == 0);` говорит, что из первого следует второе.
- **Проверяйте на этапе компиляции.** Если факт может проверить компилятор, проверяйте его там: соотношения констант, размер типа, раскладку структуры в памяти. Тогда ошибка проектирования ломает сборку, а не запуск.
- **Заменяйте утверждением комментарий** время от времени. Если факт очень важен, а читатель его не ожидает, утверждение и документирует его, и обеспечивает его соблюдение.
- **Сначала поймите, потом проверяйте.** Утверждение фиксирует то, что вы знаете; само знание оно не заменяет. Постройте мысленную модель, выразите её в утверждениях и отстаивайте её перед ревьюером в коде и комментариях.
- **Считайте фаззер последней линией защиты.** Фаззинг и симуляция идут последними, чтобы найти то, что упустили и вы, и ревьюер. Если фаззер ничего не нашёл, это не доказывает, что ничего нет.

## Состояние, память и числа

**Уровень:** профиль проекта

Держите состояние маленьким, в единственном экземпляре и рядом с местом использования. Большинство ошибок живёт в промежутке между местом, где значение проверено, и местом, где оно используется.

### Память

- **Выделяйте память при запуске и больше не выделяйте.** Если программа сама управляет памятью, задавайте размер каждого буфера и пула при инициализации, исходя из заявленного максимума. После этого ничего не выделяйте и не освобождайте. Так исключаются использование после освобождения и задержки на выделении памяти. Кроме того, это заставляет заранее спроектировать использование памяти, и система обычно получается проще и быстрее.
- **Где памятью управляет среда выполнения, задайте бюджет.** Задайте бюджет памяти и выделений для каждого горячего пути, измеряйте его профилировщиком и считайте регрессию дефектом. Ноль выделений сам по себе не цель.
- **Группируйте захват и освобождение.** Ставьте пустую строку перед строкой, которая захватывает ресурс, и после строки, которая планирует его освобождение. Пара читается как одно целое, и пропущенное освобождение сразу бросается в глаза.
- **Обнуляйте то, что не заполняете.** В хвосте частично заполненного буфера остаются старые байты. Очищайте незаполненную часть, иначе устаревшие данные могут утечь, а одинаковые входные данные — перестать давать одинаковый результат.

### Переменные

- **Используйте наименьшую область видимости.** Объявляйте переменную там, где она впервые нужна, и завершайте её жизнь, как только она больше не нужна. Чем меньше имён в поле зрения, тем меньше шансов взять не то.
- **Храните одну копию.** Значение живёт в одном месте и читается оттуда. Вторая копия или псевдоним со временем разойдутся с первой.
- **Проверяйте рядом с использованием.** Вычисляйте или проверяйте значение непосредственно перед кодом, который от него зависит. Именно в расстоянии между проверкой и использованием — в строках или во времени — допущения устаревают. Самый известный пример — ошибки класса «время проверки — время использования».
- **Передавайте большие значения по ссылке только для чтения.** Если значение большое и копия не нужна, не передавайте его по значению. Случайная копия стоит времени и может скрыть ошибку. В TigerStyle порог — 16 байт. Задайте свой порог в профиле и следуйте языку там, где копирование небольших значений — идиома.
- **Создавайте большие структуры на месте.** Инициализируйте большое значение сразу в его конечном расположении через указатель на него, а не собирайте его в другом месте с последующим перемещением. Его адрес остаётся стабильным, а стек не растёт из-за скрытых копий. Если хотя бы одно поле создаётся на месте, создавайте на месте весь контейнер.

### Конкурентность

**Применяется, когда:** одно и то же состояние могут затронуть несколько задач, потоков или процессов.

- **Выберите одну модель конкурентности для каждого компонента.** Запишите, принадлежит ли его состояние одному потоку, разделяется под блокировками или передаётся в сообщениях. От этого выбора зависит, что может измениться между двумя строками кода.
- **Выполняйте работу до конца без приостановки, где модель это позволяет.** В однопоточном кооперативном коде функция, которая не приостанавливается, сохраняет свои предусловия истинными от начала до конца. Если она уступает управление, к моменту возобновления они могут оказаться ложными.
- **Не считайте отсутствие `await` блокировкой.** Отсутствие приостановки защищает состояние только от задач в том же потоке. Другие потоки по-прежнему могут изменить всё, что с ними разделено.
- **Проверяйте и применяйте за один атомарный шаг.** После асинхронной работы проверяйте состояние, от которого зависите, и вносите изменение внутри одной и той же критической секции, транзакции или операции compare-and-swap. Повторная проверка сама по себе всё равно оставляет зазор перед записью.
- **Делайте критические секции короткими.** Выполняйте медленную и асинхронную работу вне блокировки, а блокировку берите только для проверки и применения.
- **Никогда не удерживайте обычную блокировку, которая блокирует поток, на время приостановки.** Это может привести к взаимоблокировке или остановить все задачи в потоке. Удерживайте блокировку через `await`, только если она для этого предназначена и этого требует архитектура.
- **Считайте ожидаемое конкурентное изменение конфликтом.** Отклоните операцию, сообщите о конфликте или повторите попытку. Утверждение нужно для инварианта, который гарантирует модель, а не для гонки, которую допускает архитектура.

### Числа

- **Понимайте, с какими числами имеете дело.** Целые фиксированной ширины переполняются, целые произвольной точности растут без ограничений, а числа с плавающей точкой теряют точность. Каждый вид требует своей проверки.
- **Используйте целые с явным размером, где язык их поддерживает.** Выбирайте ширину осознанно, например `u32` или `i64`, и избегайте типов, размер которых зависит от машины.
- **Считайте индекс, количество и размер тремя разными типами.** Для последовательности с нумерацией от нуля количество не меньше нуля, а корректный индекс удовлетворяет условию `0 <= index < count`. `index + 1` — число элементов до этого индекса включительно. `count - 1` — последний индекс, только если последовательность не пуста.
- **Вычисляйте размеры с проверкой переполнения.** Размер — это количество, умноженное на размер единицы, и это умножение может переполниться. Называйте переменные так, чтобы читатель мог отличить индекс от количества и от размера.
- **Явно указывайте, как округляет деление.** Используйте операцию, название которой говорит, какое это деление: точное, с округлением вниз или с округлением вверх. Тогда читатель знает, что вы подумали об остатке.

## Производительность

**Уровень:** профиль проекта

**Применяется, когда:** пропускная способность или задержка — заявленное требование. Без такого требования правило *Не пропускайте блокирующих дефектов* всё равно действует.

Производительность определяется на этапе проектирования, когда измерять ещё нечего.

- **Закладывайте производительность в архитектуру с самого начала.** Выигрыш на порядки даёт архитектура, а её труднее всего изменить, когда код уже написан. Профилирование потом может лишь отшлифовать то, что допускает архитектура.
- **Сначала прикиньте на бумаге.** Для каждого варианта архитектуры оцените пропускную способность и задержку сети, диска, памяти и процессора. Грубая прикидка дёшева, и её обычно хватает, чтобы выбрать верный вариант.
- **Работайте в согласии с железом.** Знайте, как ведёт себя оборудование, и проектируйте под него: последовательный доступ, данные, которые остаются в кэше, ввод-вывод пакетами.
- **Сначала оптимизируйте самый медленный ресурс.** Обычный порядок: сеть, диск, память, процессор. Затем учтите, как часто используется каждый ресурс. Обращение к памяти в горячем цикле в сумме может стоить больше, чем один сетевой вызов на запрос.
- **Принимайте решения на пакет, а не на элемент.** Отделяйте плоскость управления, которая принимает решения, от плоскости данных, которая выполняет работу. Тогда путь управления может позволить себе тяжёлые проверки, а путь данных остаётся компактным.
- **Обрабатывайте пакетами, чтобы амортизировать затраты.** Платите фиксированную цену — системный вызов, сетевой обмен туда и обратно или сброс на диск — один раз на пакет, а не один раз на элемент.
- **Держите процессор на прямой.** Предсказуемый код — быстрый код. Давайте процессору длинные серии однотипной работы, а не заставляйте его прыгать между несвязанными задачами.
- **Не рассчитывайте на оптимизатор.** Пишите быстрый путь явно. Горячему циклу место в отдельной функции, аргументы которой — простые значения, а не объект с полями. Тогда ничего не зависит от того, докажет ли компилятор, что поле не меняется посреди цикла, а дублирующуюся работу легко заметить.

## Зависимости и инструменты

**Уровень:** профиль проекта

Каждая зависимость и каждый инструмент — это издержки, которые вы несёте всё время жизни проекта.

- **Стремитесь к нулю зависимостей.** Помимо инструментария языка, каждая зависимость приносит риски цепочки поставок, ошибки, которые вы не можете исправить, производительность, которую вы не контролируете, и более медленную установку. В фундаментальном ПО всё, что построено поверх, наследует эти издержки.
- **Отвечайте за исключения.** Если без зависимости не обойтись, запишите, почему, зафиксируйте её версию и читайте её код так же внимательно, как собственный.
- **Держите набор инструментов маленьким.** Каждый лишний инструмент всем приходится устанавливать, изучать, обновлять и отлаживать. В первую очередь берите инструмент, которым команда уже пользуется, даже если специализированный справился бы чуть лучше.
- **Пишите скрипты на основном языке проекта.** Пишите скрипты сборки и выпуска на языке кодовой базы. Тогда их проверяет тот же компилятор, они запускаются везде, где работает код, и сопровождать их может любой в команде. Shell-скрипт ломается на той единственной машине, где оболочка отличается.
- **Стандартизируйте рано.** Каждый новый участник команды приносит любимые инструменты, и разнообразие нарастает. Договорённость об одном инструменте стоит отдельному человеку немного скорости сейчас и экономит команде гораздо больше потом.
- **Включите все предупреждения компилятора с самого начала.** Используйте самый строгий уровень, который есть у компилятора, и пусть любое предупреждение ломает сборку. Предупреждение, которое терпят с самого начала, становится шумом и скрывает то единственное, которое важно.

## Функции

**Уровень:** локальное соглашение

Функция — единица ревью: делайте её короткой, с узким интерфейсом и видимым контрактом.

### Форма

- **Ограничивайте каждую функцию 70 строками.** Это примерно один экран, а функцию, которую видно целиком, можно целиком и проверить. Это число — настройка TigerStyle (*Считайте настройки TigerStyle лишь одним примером профиля*). Найти разбиение, которое хорошо читается, — в этом и состоит мастерство.
- **Делайте концы узкими, а середину широкой.** Хорошая функция принимает мало параметров, возвращает что-то простое, а между этим выполняет настоящую работу.
- **Ветвления — в родительской функции, циклы — во вспомогательных.** Если функция слишком разрослась, разделите её так, чтобы каждое решение оставалось в одном месте. Родительская функция выбирает, что делать; вспомогательные функции делают это без ветвлений ([Push Ifs Up And Fors Down](https://matklad.github.io/2023/11/15/push-ifs-up-and-fors-down.html)).
- **Меняйте состояние в одном месте.** Вспомогательные функции вычисляют и возвращают результат. Только родительская функция применяет результат к своему локальному состоянию, поэтому у функций-листьев нет побочных эффектов.
- **Возвращайте наименьший тип, который полностью выражает контракт.** Каждый исход, который может вернуть функция, становится ветвлением в коде каждой вызывающей функции, поэтому не возвращайте больше, чем операция способна произвести.
- **Сохраняйте исходы, которые вызывающий код должен различать.** Не сливайте разные отказы и не скрывайте ошибку ради более простой сигнатуры. Вызывающий код может обработать только то, о чём ему сообщает контракт. **Уровень:** базовое требование

### Места вызова

- **Именуйте аргументы, которые можно перепутать.** Функция с двумя параметрами одного типа получает именованные аргументы или структуру параметров: `resize({ width, height })`, а не `resize(width, height)`.
- **Делайте отсутствующий аргумент читаемым.** Если аргумент может быть null, место вызова должно по имени показывать, что именно опущено.
- **Передавайте долгоживущие зависимости позиционно.** У аллокатора, часов или трассировщика свой собственный тип, и их нельзя перепутать друг с другом. Передавайте их конструкторам позиционно, в фиксированном порядке: от общего к частному.
- **Ставьте колбэки последними.** Они выполняются последними, поэтому и читаются последними.
- **Явно указывайте важные параметры библиотек.** Если значение по умолчанию влияет на корректность, безопасность, надёжность хранения или расход ресурсов, укажите параметр в вызове или в той единственной обёртке, которую использует кодовая база. Тогда обновление, которое меняет значение по умолчанию, не изменит поведение вашего кода у вас за спиной. Повторять каждое косметическое значение по умолчанию — значит лишь добавлять шум.

### Условия

- **Разбивайте составное условие, если его случаи различаются.** Если части требуют разной обработки или всё условие трудно проверить, используйте вложенные простые ветвления `if`/`else`, чтобы каждый случай был виден. Так же разворачивайте длинные цепочки `else if`. Короткое условие, которое выражает одну мысль, или именованный предикат можно оставить целиком.
- **Учитывайте другую ветвь каждого `if`.** Решите, что означает `else`: обработайте его, проверьте утверждением, что он невозможен, или опустите его, если охранное условие уже всё сказало. Цель в том, чтобы ни один случай не остался без внимания, а не в том, чтобы у каждого `if` появился `else`.
- **Формулируйте условия в положительной форме.** Проверяйте состояние, в котором всё правильно, например `if (length <= capacity)`, а отказ помещайте в `else`. В отрицательных проверках легко ошибиться на единицу.

## Именование

**Уровень:** локальное соглашение

Имена — главный интерфейс к коду, поэтому не жалейте на них времени.

- **Выбирайте существительные и глаголы внимательно.** Хорошее имя без всякого комментария говорит читателю, что это такое или что оно делает. Ищите дальше, пока имена в модуле не будут так же хорошо согласованы друг с другом, как с тем, что они называют.
- **Используйте `snake_case` для функций, переменных и файлов**, если язык оставляет выбор за вами. Слова, разделённые подчёркиваниями, читаются почти как обычный текст, и ни у кого не возникает соблазна сократить имя ради читаемости.
- **Не сокращайте.** Пишите `connection_count`, а не `conn_cnt`. Однобуквенное имя допустимо только для простой целочисленной переменной в сортировке или матричных вычислениях.
- **Пишите флаги в скриптах полностью.** `--verbose` объясняет себя сам. `-v` — для ручного ввода в командной строке.
- **Пишите аббревиатуры целиком заглавными буквами.** `HTTPServer`, а не `HttpServer`.
- **Ставьте единицы измерения и уточнения в конец, а самое значимое слово — в начало.** `retry_delay_ms_max` и `retry_delay_ms_min` при сортировке оказываются рядом и выравниваются друг под другом, а всё, что относится к задержке повтора, собрано в одну группу.
- **Пусть имя несёт обязательства.** `scratch_buffer` сообщает читателю, что содержимое не переживёт вызова. `buffer` не сообщает ничего.
- **Давайте связанным именам одинаковую длину.** Выбирайте `lower` и `upper` или `client` и `server`. Тогда производные имена, такие как `client_address` и `server_address`, выравниваются, а асимметрия в коде сразу бросается в глаза.
- **Начинайте имя вспомогательной функции с имени вызывающей.** Вспомогательная функция или колбэк, которые обслуживают одну функцию, получают её имя как префикс: `flush_batch()` и `flush_batch_callback()`. Тогда уже по имени видно, кто её вызывает.
- **Давайте каждому имени одно значение.** Если `node` уже означает узел кластера, элементу дерева нужно другое слово. Термин, значение которого зависит от контекста, будут понимать неправильно.
- **Выбирайте имена, которые работают и вне кода.** Имена попадают в документы, задачи и разговоры. Существительное вроде `queue.backlog` можно использовать там без изменений, и оно естественно расширяется до `backlog_max`. Прилагательное или причастие вроде `queue.waiting` каждый раз приходится перефразировать.
- **Ставьте главное в начало.** Файл читают сверху вниз, поэтому важное идёт туда, а `main` — первым. Внутри типа сначала идут поля, затем вложенные типы, затем методы.
- **Выносите и сортируйте, где это помогает.** Переносите сложный вложенный тип на верхний уровень. Где естественного порядка нет, сортируйте по алфавиту: имена, которые начинаются с самого значимого слова, тогда сами собираются в группы.
- **Во всём остальном следуйте стандартному руководству по стилю для вашего языка.**

| Целые числа явного размера | Никаких сюрпризов в арифметике | Фиксированная разрядность (C, Go, Rust, Zig): указывайте разрядность явно, а типы с платформенным размером, такие как `int` или `usize`, преобразуйте приведением с проверкой. Произвольная точность (`int` в Python, `BigInt` в JavaScript): проверяйте допустимый диапазон предметной области и ограничивайте размер, потому что обработка огромного значения требует времени и памяти. Плавающая точка (`Number` в JavaScript — это IEEE 754 binary64): для целочисленного поля требуйте `Number.isSafeInteger` и проверку диапазона, а для бо́льших точных значений используйте `BigInt`. |
| Утверждения всегда включены | Сбой в месте нарушения инварианта, в том числе в продакшене | `assert` в C исчезает при `NDEBUG`, `assert` в Python — при `-O`, а `debug_assert!` в Rust — в релизных сборках по умолчанию. `assert` в Java выключен, пока его не включат явно. Используйте проверку, которую нельзя убрать при компиляции, следите, чтобы у неё не было побочных эффектов, и убедитесь, что происходит при сбое: в ряде языков возникает исключение, которое код может перехватить. |
| Утверждения времени компиляции | Ошибки проектирования ломают сборку | `static_assert` в C и C++, утверждение в `const` в Rust, `comptime` в Zig. Если такой возможности нет, вынесите проверки в тест, который запускается при каждой сборке. |
| Без рекурсии | Ограниченное выполнение | Где рекурсия — идиома языка, как в функциональных языках, используйте ограниченную форму из правила *Запретите рекурсию или ограничьте её*. |
| Именованные аргументы | Места вызова, где аргументы невозможно перепутать | Именованные аргументы (Python, Swift, Kotlin), структура или объект параметров (C, Go, Rust, Zig, TypeScript) либо отдельный тип-обёртка для каждого вида значения. |
| Передача по ссылке, построение на месте | Никаких случайных копий | Это относится к языкам с семантикой значений, а порог размера задаётся в профиле. При ссылочной семантике риск обратный — случайное совместное использование: копируйте намеренно и не создавайте псевдонимов изменяемых объектов. |
| Выполнение до конца без приостановки | Предусловия выполняются на всём протяжении | Гарантия действует в пределах одного хода одного потока. При `async`/`await`, корутинах или потоках действуют правила раздела «Конкурентность», и первое из них — *Проверяйте и применяйте за один атомарный шаг*. |
| Обработка каждой ошибки | Никаких молчаливых сбоев | При исключениях: никаких пустых `catch`, и перехватывайте только то, что можете обработать. При кодах возврата: сделайте игнорирование результата ошибкой компилятора или линтера (`[[nodiscard]]`, `#[must_use]`, `errcheck`). |
| Округление и переполнение | Намерение видно в арифметике | Поведение по умолчанию различается между языками и даже между режимами сборки. Явно указывайте способ округления и поведение при переполнении везде, где язык даёт выбор. |
| Форматирование и регистр имён | Единый вид всего кода | Если экосистема закрепляет соглашение (табуляция в `gofmt`, экспорт через заглавную букву в Go, camelCase в Java), побеждает оно. Важны единообразие и описательные имена. |

## Внедрение руководства

Внедряйте руководство в шесть шагов и храните результат в репозитории в виде короткого файла профиля. Первый шаг обязателен, потому что руководство не предназначено для применения целиком.

1. **Отберите то, что применимо.** Перечислите специальные блоки и условные правила, которые действуют в этом проекте (*Включайте специальный блок по его условию*). Сделайте это до того, как выбирать какие-либо механизмы или числа. Специальный блок не применяется, только если не выполнено заявленное в нём условие применимости. Если вы не включили его в профиль, это не отменяет применимое правило.
2. **Выберите профиль проекта.** Определите механизмы для всего, что применимо: стратегию работы с памятью, политику в отношении рекурсии, модель конкурентности и политику утверждений. Запишите каждое решение вместе с его причиной.
3. **Задайте лимиты ресурсов.** Перечислите каждый ограниченный ресурс с его лимитом (*Ограничивайте всё*).
4. **Задайте реакцию на каждый лимит.** Опишите, что происходит при его превышении (*Определите, что происходит на лимите*).
5. **Автоматизируйте проверки.** Включите в сборку форматтер, правила линтера, ограничения длины и тесты для каждого лимита. Правило, которое держится только на ревью, со временем перестаёт соблюдаться.
6. **Запишите исключения и открытые вопросы.** Следуйте процедуре из правила *Записывайте каждое исключение из правил* и храните открытые вопросы в профиле рядом с исключениями.

Для каждого лимита укажите единицу измерения, область действия, место проверки и то, что происходит при превышении. Значения ниже — примеры.

## Примеры

Пять коротких случаев на псевдокоде показывают, как правила выглядят на практике.

### Граница доверия

Недоверенные байты разбираются один раз, поле за полем, в типы, которые не могут содержать недопустимое значение. `parse_account_id` устроена так же, как `parse_amount`.

```
// Контракт: функция возвращает Amount — целое число, для которого 1 <= amount <= amount_max, — или ошибку.
function parse_amount(raw): Amount | ParseError {
    if (!is_integer(raw)) return ParseError.amount_not_integer;
    if (raw < 1) return ParseError.amount_too_small;
    if (raw > amount_max) return ParseError.amount_too_large;
    return Amount(raw);
}

// На границе: плохие входные данные — эксплуатационная ошибка, поэтому её возвращают, а не проверяют утверждением.
function parse_transfer(bytes): Transfer | ParseError {
    if (bytes.length > transfer_bytes_max) return ParseError.too_large;
    const fields = decode(bytes);
    if (fields == null) return ParseError.malformed;
    const account_id = parse_account_id(fields.account_id);
    if (is_error(account_id)) return account_id;
    const amount = parse_amount(fields.amount);
    if (is_error(amount)) return amount;
    return Transfer { account_id, amount };
}

// За границей: принимаются только разобранные типы. Плохое значение здесь — это баг.
function apply_transfer(transfer: Transfer) {
    assert(transfer.amount >= 1);
    assert(transfer.amount <= amount_max);
    // ...
}
```

### Утверждения

Ожидаемый сбой обрабатывается. Внутренний инвариант проверяется утверждениями (`assert`), по одному условию за раз, — там, где значение записывается, и ещё раз там, где оно читается.

```
function append(log: Log, record: Record): Ok | Error {
    // Эксплуатационная ошибка: журнал рано или поздно заполнится, поэтому вызывающий код получает ошибку.
    if (log.count == log.count_max) return Error.log_full;

    // Ошибка программиста: вызывающий код обязан передать уже проверенную запись.
    assert(record.size > 0);
    assert(record.size <= record_size_max);

    log.records[log.count] = record;
    log.count += 1;
    return Ok;
}

function read(log: Log, index: u32): Record {
    assert(index < log.count);  // Индекс беззнаковый, поэтому достаточно одной этой границы.
    const record = log.records[index];

    // Те же два свойства проверяются утверждениями ещё раз там, где запись читается.
    assert(record.size > 0);
    assert(record.size <= record_size_max);
    return record;
}
```

### Состояние вокруг `await`

Проверка, сделанная до приостановки, после неё уже устарела. Сначала выполните медленную работу, затем проверьте и примените изменение за один атомарный шаг.

```
// Неправильно: баланс может измениться, пока запрашивается лимит.
async function withdraw(account, amount: Amount) {
    if (account.balance < amount) return Error.insufficient_funds;
    const limit = await fetch_withdrawal_limit(account.id);  // Здесь выполняются другие задачи.
    if (amount > limit) return Error.over_limit;
    account.balance -= amount;                               // Проверка баланса уже устарела.
    return Ok;
}

// Правильно: между проверкой баланса и записью нет ни одной приостановки.
async function withdraw(account, amount: Amount) {
    // Политика: лимит на одно снятие, прочитанный в начале, действует только в пределах этой одной операции.
    const limit = await fetch_withdrawal_limit(account.id);
    if (amount > limit) return Error.over_limit;
    return account.update(function (state) {
        if (state.balance < amount) return Error.insufficient_funds;
        state.balance -= amount;
        return Ok;
    });
}
```

`account.update` обозначает атомарный шаг выбранной модели: короткую критическую секцию, транзакцию или один ход однопоточного выполнения. Конкурентное снятие тогда проявляется как обычный отказ, а не как сработавшее утверждение. Для дневного лимита этого мало: уже потраченную сумму пришлось бы проверять и обновлять внутри того же атомарного шага.

### Типы возврата

Тип перечисляет все исходы, которые должен обработать вызывающий код, и ничего лишнего.

```
// Скрывает ошибку: null означает и «нет такого пользователя», и «хранилище недоступно».
function find_user(id): User | null

// Описывает весь контракт: три исхода, и каждый обрабатывает вызывающий код.
function find_user(id): User | NotFound | StoreError

// Функция не может завершиться ошибкой и всегда даёт ответ, поэтому тип остаётся минимальным.
function user_count_max(): u32
```

### Повторные запросы

Что означает дубликат, решает протокол. Здесь каждая попытка попадает в журнал аудита, повтор возвращает первый результат, а перевод применяется один раз. Тот же ключ с другим содержимым — это конфликт.

```
// Ключ идемпотентности действует в пределах одного клиента: (client_id, request.id).
function handle_transfer(client_id, request) {
    audit_log.append(client_id, request);  // Записывается каждая попытка, включая дубликаты.

    // Один атомарный шаг: найти ключ, применить перевод, запомнить результат.
    return store.transaction(function (tx) {
        const key = { client_id, request_id: request.id };
        const earlier = tx.results.get(key);
        if (earlier == null) {
            const result = tx.apply_transfer(request.transfer);
            tx.results.put(key, { transfer: request.transfer, result });
            return result;
        } else {
            if (earlier.transfer != request.transfer) return Error.key_conflict;
            return earlier.result;  // На дубликат отвечают, но повторно его не применяют.
        }
    });
}

test "a replayed transfer is applied once and audited twice" {
    const first = handle_transfer(client_id, request);
    const second = handle_transfer(client_id, request);

    assert(second == first);
    assert(balance(request.transfer.account_id) == balance_before - request.transfer.amount);
    assert(audit_log.count == audit_count_before + 2);
}
```
